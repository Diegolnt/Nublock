# M0 — Setup: proyecto, config, logging, CLI y tests

**Objetivo del milestone:** tener un proyecto Python instalable, con lint, tests, logging y carga de
configuración validada. DoD (Definition of Done): `pytest` pasa y `python -m nublock --help` funciona.

Archivos de este milestone:

| Archivo | Qué contiene |
|---|---|
| `pyproject.toml` | Metadata del proyecto, dependencias, config de pytest y ruff |
| `src/nublock/__init__.py` | Marca el paquete y define `__version__` |
| `src/nublock/__main__.py` | Entry point de `python -m nublock` |
| `src/nublock/cli.py` | CLI (Command-Line Interface) con `argparse` |
| `src/nublock/config.py` | Modelos pydantic + `load_config()` |
| `src/nublock/paths.py` | Rutas por OS con `platformdirs` |
| `src/nublock/logging_setup.py` | `logging` a archivo rotativo + consola |
| `config/config.example.yaml` | Config de ejemplo (macOS) |
| `tests/test_config.py`, `tests/test_cli.py` | Tests del config loader y la CLI |

Cómo probarlo:

```bash
source .venv/bin/activate
python -m nublock --help
python -m nublock --config config/config.example.yaml config
pytest tests/test_config.py -v
ruff check .
```

## 1. Herramientas del proyecto

### `venv` (virtual environment)
- **Qué hace:** crea una carpeta (`.venv/`) con un Python aislado. Lo que instales ahí no afecta al
  Python del sistema ni a otros proyectos.
- **Uso:** `python3 -m venv .venv` crea el entorno; `source .venv/bin/activate` lo activa en tu
  terminal (después de eso, `python` y `pip` apuntan a `.venv/bin/`).
- **Argumentos:** la ruta de la carpeta a crear (`.venv`).
- **Retorna:** nada; crea archivos. El `-m` de `python -m venv` significa "ejecuta el módulo
  `venv` como programa".

### `pip install -e ".[dev]"`
- **Qué hace:** instala el proyecto en modo *editable* (`-e`): Python importa `nublock` directo
  desde `src/`, así tus cambios se ven sin reinstalar. `.[dev]` = "este directorio (`.`) más las
  *optional dependencies* del grupo `dev`" (pytest y ruff).
- **Retorna:** nada; instala paquetes en el venv.

### `pyproject.toml`
Archivo estándar (PEP 621, *Python Enhancement Proposal*) que describe el proyecto en formato TOML
(*Tom's Obvious Minimal Language*):
- `[build-system]`: qué herramienta construye el paquete. Usamos **hatchling** (*build backend*):
  `requires` lista lo que pip debe instalar para construir y `build-backend` el módulo a usar.
- `[project]`: nombre, versión, `requires-python`, `dependencies` (runtime).
  `"pyobjc-framework-Cocoa>=10.3; sys_platform == 'darwin'"` usa un *environment marker*: solo se
  instala si el OS es macOS (`darwin`).
- `[project.optional-dependencies]`: grupos opcionales, ej. `dev`.
- `[project.scripts]`: `nublock = "nublock.cli:main"` crea un comando `nublock` en el venv que
  llama a la función `main` del módulo `nublock.cli`.
- `[tool.hatch.build.targets.wheel] packages = ["src/nublock"]`: dónde está el código (*src
  layout*: el código vive en `src/` para que los tests usen el paquete instalado, no archivos
  sueltos).
- `[tool.pytest.ini_options]` y `[tool.ruff]`: configuración de esas herramientas.

### ruff
- **Qué hace:** *linter* (encuentra errores y malas prácticas) y *formatter* (da formato
  consistente) muy rápido, escrito en Rust.
- **Comandos:** `ruff check .` (lint; `--fix` corrige lo automático), `ruff format .` (formatea),
  `ruff format --check .` (solo verifica).
- **Config (`[tool.ruff.lint] select`)**: familias de reglas activadas:
  `E`/`W` (pycodestyle: estilo), `F` (pyflakes: imports sin usar, variables indefinidas),
  `I` (isort: orden de imports), `UP` (pyupgrade: sintaxis moderna), `B` (bugbear: bugs comunes),
  `ANN` (*annotations*: exige type hints en todas las funciones).
- `extend-exclude = [".venv", "*.md"]`: carpetas/archivos que ruff ignora (ver DECISIONS.md #7).

### pytest
- **Qué hace:** framework de tests. Busca archivos `test_*.py` en `testpaths` (`tests/`), ejecuta
  cada función `test_*` y reporta las que fallan. Un test falla si un `assert` es falso o si lanza
  una excepción no esperada.
- **Retorna:** exit code 0 si todo pasó, distinto de 0 si algo falló.
- `addopts = "-ra"`: al final muestra un resumen de tests saltados/fallidos.

Piezas de pytest usadas en los tests:

| API | Qué hace | Argumentos | Retorna |
|---|---|---|---|
| `@pytest.fixture` | Declara una *fixture*: una función que prepara algo (ej. una DB) y pytest la inyecta en cualquier test que tenga un parámetro con ese nombre. Con `yield`, lo que viene después es la limpieza (*teardown*) | `autouse=True` (opcional): se aplica a todos los tests del archivo sin pedirla | Lo que la fixture hace `yield`/`return` |
| `pytest.raises(ExcType, match=...)` | *Context manager* que verifica que el bloque `with` lance esa excepción | `ExcType`: clase esperada; `match`: regex que debe aparecer en el mensaje | Un `ExceptionInfo` (`.value` es la excepción) |
| `@pytest.mark.parametrize("a", [v1, v2])` | Ejecuta el mismo test una vez por cada valor | nombre(s) de parámetros (str o tupla) y lista de valores | — |
| `tmp_path` (fixture integrada) | Carpeta temporal única por test | — | `pathlib.Path` |
| `monkeypatch` (fixture integrada) | Reemplaza atributos temporalmente; se deshace solo al terminar el test | `monkeypatch.setattr(objeto, "nombre", nuevo_valor)` | `None` |
| `capsys` (fixture integrada) | Captura lo que se imprime en stdout/stderr | `capsys.readouterr()` | Objeto con `.out` y `.err` (`str`) |

`tests/conftest.py`: archivo especial que pytest carga solo; las fixtures definidas ahí (ej.
`repo`) están disponibles en todos los tests. Una fixture con `yield` es un *generator*, por eso su
type hint es `collections.abc.Iterator[Repository]` ("algo que produce valores `Repository` uno a
uno"). `tests/helpers.py` tiene helpers normales (no fixtures) que los tests importan con
`from helpers import ...` (pytest agrega la carpeta `tests/` al `sys.path`).

## 2. Cómo arranca `python -m nublock`

- `python -m nublock` ejecuta el archivo `src/nublock/__main__.py` del paquete.
- `raise SystemExit(main())`: `SystemExit(code)` es la excepción que termina el programa con ese
  *exit code* (0 = éxito). Es lo mismo que hace `sys.exit(code)`.
- `__init__.py` convierte la carpeta en un *package*; `__version__ = "0.1.0"` es una convención para
  exponer la versión.

## 3. `argparse` (stdlib) — la CLI

`argparse` convierte la lista de argumentos de la terminal en un objeto con atributos, y genera
`--help` automáticamente.

| API | Qué hace | Argumentos principales | Retorna |
|---|---|---|---|
| `argparse.ArgumentParser(prog, description)` | Crea el parser principal | `prog`: nombre del programa en el help; `description`: texto del help | `ArgumentParser` |
| `parser.add_argument(*names, **opts)` | Declara una opción o argumento posicional | `"--config"` (opción) o `"period"` (posicional); `type=Path` convierte el string; `action="store_true"` → `True` si aparece la flag; `action="version"` imprime la versión y sale; `choices=[...]` valores permitidos; `nargs="?"` 0 o 1 valor; `default`; `metavar` nombre mostrado; `help` | un `Action` (no lo usamos) |
| `parser.add_subparsers(dest, required, metavar)` | Habilita subcomandos (`run`, `report`, `config`) | `dest="command"`: atributo donde queda el nombre; `required=True`: obliga a dar uno | Un objeto con `.add_parser()` |
| `subparsers.add_parser(name, help)` | Crea el parser de un subcomando | nombre y texto de ayuda | `ArgumentParser` |
| `parser.set_defaults(handler=fn)` | Agrega atributos fijos al resultado si se elige ese subcomando. Lo usamos para guardar qué función ejecuta cada subcomando | `**kwargs` | `None` |
| `parser.parse_args(argv)` | Parsea; si `argv` es `None` usa `sys.argv[1:]`. Con `--help` o errores imprime y lanza `SystemExit` | lista de strings o `None` | `argparse.Namespace` (objeto con un atributo por argumento, ej. `args.config`) |

En `cli.py`, `main()` hace: parsear → configurar logging → cargar config → llamar
`args.handler(args, context)`.

## 4. Configuración: PyYAML + pydantic

### PyYAML (`import yaml`)
- **`yaml.safe_load(stream)`**
  - **Qué hace:** convierte texto YAML en objetos Python (`dict`, `list`, `str`, `int`, `float`,
    `bool`, `None`). *Safe* = no construye objetos Python arbitrarios (evita ejecutar código desde
    el archivo).
  - **Argumentos:** `stream`: un `str` o un archivo abierto.
  - **Retorna:** el objeto Python (un archivo vacío retorna `None`).
  - **Lanza:** `yaml.YAMLError` si la sintaxis es inválida.
- **Ojo (YAML 1.1):** `13:00` sin comillas se lee como el entero `780` (notación sexagesimal, base
  60). Por eso las horas van entre comillas: `"13:00"`.
- También se usa `yaml.safe_dump(data, stream, sort_keys=False, allow_unicode=True)` solo en el
  script de demo (escribe un objeto Python como YAML).

### pydantic (v2)
Valida datos contra clases con type hints. Si un dato no cumple, lanza `ValidationError`
explicando cada problema.

| API | Qué hace | Argumentos | Retorna |
|---|---|---|---|
| `class X(BaseModel)` | Define un modelo: cada atributo anotado es un campo validado | — | — |
| `ConfigDict(extra="forbid", frozen=True)` | Configura el modelo (en `model_config`). `extra="forbid"`: keys desconocidas son error; `frozen=True`: inmutable y *hashable* | opciones por keyword | un dict de config |
| `Field(default=..., gt=0, ge=1, min_length=1, discriminator="type")` | Restricciones de un campo: `gt` (*greater than*), `ge` (*greater or equal*), `min_length` (listas/strings), `discriminator` (ver abajo) | keywords | metadata del campo |
| `@field_validator("campo", mode="before")` + `@classmethod` | Función propia que valida/transforma un campo. `mode="before"` corre antes de la conversión de tipos (ve el valor crudo del YAML); por defecto (`"after"`) recibe el valor ya convertido | nombres de campos, `mode` | La función debe retornar el valor (posiblemente transformado) o lanzar `ValueError` |
| `@model_validator(mode="after")` | Valida el modelo completo (relaciones entre campos, ej. "exactamente una key") | `mode` | La función retorna `self` o lanza `ValueError` |
| `Model.model_validate(data)` | Construye y valida un modelo desde un `dict` | `data` | instancia del modelo |
| `instance.model_copy(update={...})` | Copia con algunos campos cambiados (útil con modelos `frozen`) | `update`: dict | nueva instancia |
| `ValidationError` | Excepción con la lista de errores; `str(exc)` es legible | — | — |

Tipos usados en los campos:
- `Literal["productive", "neutral", "distracting"]` (`typing`): solo esos valores exactos.
- `str | None`: puede ser string o `None` (opcional).
- `datetime.time`: pydantic convierte `"09:00"` en `time(9, 0)`.
- `Annotated[DailyLimitRule | ScheduleRule, Field(discriminator="type")]`: *discriminated union*;
  pydantic mira el campo `type` (`"daily_limit"` o `"schedule"`) para elegir el modelo, y da
  errores claros si no coincide ninguno.
- `dict[str, Any]`: dict sin validar (secciones de milestones futuros).

### Nuestras funciones (`config.py`)
- **`load_config(path: Path | None) -> Config`**: con `None` retorna los defaults; si no, lee el
  archivo, `yaml.safe_load`, y `Config.model_validate`. Envuelve `FileNotFoundError`,
  `yaml.YAMLError` y `ValidationError` en nuestra `ConfigError` con un mensaje claro.
- Modelos: `GeneralConfig`, `MatchConfig`, `ClassificationRule`, `RuleTarget`, `DailyLimitRule`,
  `ScheduleRule`, `Config`.

### `re` (stdlib, usado para validar `title_regex`)
- **`re.compile(pattern)`**: compila una *regular expression*. **Retorna** `re.Pattern`. **Lanza**
  `re.error` si la regex es inválida. En el validador la compilamos solo para detectar errores al
  cargar la config (y no a mitad de la ejecución). Detalle en M2.md.

## 5. `pathlib` (stdlib) — rutas de archivos

`pathlib.Path` representa una ruta como objeto (en vez de strings).

| API | Qué hace | Retorna |
|---|---|---|
| `Path("a") / "b"` | Une rutas con `/` | `Path` |
| `path.exists()` | ¿Existe el archivo/carpeta? | `bool` |
| `path.read_text(encoding="utf-8")` / `path.write_text(text, encoding=...)` | Lee / escribe el archivo completo como texto | `str` / `int` (caracteres escritos) |
| `path.mkdir(parents=True, exist_ok=True)` | Crea la carpeta; `parents` crea las intermedias; `exist_ok` no falla si ya existe | `None` |
| `path.parent` | Carpeta contenedora | `Path` |
| `Path(__file__).resolve().parents[1]` | Ruta absoluta del archivo actual y su "abuelo" (usado en tests para ubicar `config/`) | `Path` |

## 6. `platformdirs` — dónde guardar datos según el OS

| Función | Qué retorna en macOS |
|---|---|
| `platformdirs.user_config_path(appname)` | `~/Library/Application Support/<appname>` |
| `platformdirs.user_data_path(appname)` | `~/Library/Application Support/<appname>` |
| `platformdirs.user_log_path(appname)` | `~/Library/Logs/<appname>` |

- **Argumentos:** `appname` (`"nublock"`). Hay más opcionales (`appauthor`, `version`) que no usamos.
- **Retorna:** `pathlib.Path` (no crea la carpeta; eso lo hacemos con `mkdir`).
- En Windows/Linux retornan las carpetas estándar de esos OS, por eso el código es portable.

## 7. `logging` (stdlib)

El sistema de logging tiene **loggers** (quién emite), **handlers** (a dónde va) y **formatters**
(cómo se ve). Cada mensaje tiene un nivel: `DEBUG < INFO < WARNING < ERROR < CRITICAL`.

| API | Qué hace | Argumentos | Retorna |
|---|---|---|---|
| `logging.getLogger(name)` | Obtiene (o crea) un logger. Usamos `__name__` (ej. `nublock.app`) para saber de qué módulo viene cada línea. Sin nombre: el *root logger* | `name: str` | `Logger` |
| `logger.debug/info/warning(msg, *args)` | Emite un mensaje. Los `%s`/`%d` se reemplazan con `args` solo si el mensaje se va a mostrar (más eficiente que un f-string) | mensaje y argumentos | `None` |
| `logger.setLevel(level)` | Nivel mínimo que el logger deja pasar | `logging.DEBUG`, etc. | `None` |
| `logger.addHandler(h)` / `logger.handlers.clear()` | Agrega / quita handlers | handler | `None` |
| `logging.StreamHandler()` | Handler que escribe en `stderr` | `stream` opcional | `StreamHandler` |
| `logging.handlers.RotatingFileHandler(filename, maxBytes, backupCount, encoding)` | Escribe a un archivo y, al pasar `maxBytes`, lo renombra a `.1`, `.2`… guardando `backupCount` copias | ruta, tamaño máximo, nº de backups | handler |
| `handler.setLevel(level)` / `handler.setFormatter(fmt)` | Nivel mínimo y formato de ese handler | — | `None` |
| `logging.Formatter(fmt)` | Plantilla del mensaje: `%(asctime)s` fecha, `%(levelname)s` nivel, `%(name)s` logger, `%(message)s` texto | string de formato | `Formatter` |

Nuestra `setup_logging(log_dir, verbose) -> Path`: archivo rotativo (INFO, o DEBUG con `-v`) +
consola (WARNING, o INFO con `-v`). Retorna la ruta del archivo de log.
Privacidad (NFR-09): nunca se loguean títulos de ventana.

## 8. Otras piezas de Python usadas en M0

- **Type hints** (`def f(x: int) -> str:`): documentan tipos; ruff (`ANN`) exige que existan.
- **`from __future__ import annotations`**: guarda las anotaciones como texto y las evalúa después;
  permite usar el nombre de una clase dentro de su propia definición (ej. `-> MatchConfig`).
- **`typing.Literal`, `typing.Annotated`, `typing.Any`**: ver tabla de pydantic.
- **`@dataclass(frozen=True)`** (`dataclasses`): genera `__init__`, `__repr__` y `__eq__` a partir
  de los atributos anotados; `frozen=True` lo hace inmutable. Usado en `cli._Context`.
- **`collections.abc.Sequence`**: tipo genérico para "lista o tupla" (`main(argv: Sequence[str] | None)`).
- **`sys.stderr`** y `print(..., file=sys.stderr)`: imprimir errores en el canal de errores.
- **`sys.platform`**: string del OS (`"darwin"` en macOS, `"win32"`, `"linux"`).
